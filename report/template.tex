\section{结论摘要}
\begin{itemize}
\item 稠密几何积是唯一的热点原语：每对 blade 约 0.78--1.06 ns，维度每增加 1 总成本约乘 4。
\item n$\ge$9 的符号表悬崖已消除：\texttt{gp} 从 40.14 ms 降到 0.916 ms（43.8$\times$）；
      Cl(10) 符号表按需构建，最多约 4 MiB。
\item E3/PGA3 快速路径：E3 旋转 16.1 ns（通用 69.7 ns），PGA 点变换 29.0 ns（通用 144.1 ns）。
\item 批量 SoA 在 N$\ge$100 时约为逐元素路径的 1.5--1.7 倍，每点分配 128 B（逐元素 169 B）。
\item JOML 单次运算快 3--13 倍；适配层是开销：motor 转 Matrix4f 约 364 ns，
      Blaze3D 每次重算矩阵约 370 ns。
\item C2 相对仅 C1 在稠密路径上快 3.07 倍；快速路径仅 1.86 倍。
\end{itemize}

\section{与 JOML 对比}
%%JOML%%

\begin{figure}[htbp]\centering
\includegraphics[width=0.9\textwidth]{figures/fig-joml.pdf}
\caption{GA 与 JOML：单次运算与转换成本。}\label{fig:joml}
\end{figure}

JOML 使用 float 且多数 API 原地写回，因此单次四元数/矩阵变换快 3--13 倍；GA 路径返回
不可变 \texttt{Multivector}，包含一次分配。真正的差异来自适配层：
\texttt{Blaze3D.matrix(motor)} 每次调用重算旋转矩阵与平移（约 364 ns），
\texttt{Blaze3D.transform} 每次重算矩阵（约 370 ns），比直接 sandwich 慢 12 倍。
渲染热路径应缓存 \texttt{Matrix4f}。float JOML 与 double GA 的坐标最大差为 3.7e-7。

\section{压力测试}
%%STRESS%%

\section{高维稀疏与按需符号表}
%%BIGSPARSE%%

把输出表示改为（mask, value）COO 列表后，几何积的循环范围从 $4^n$ 对降到
$k^2$ 对，低密度时用开放寻址累加，高密度时才退回稠密累加器。
$n=10$、$k=10$（约 1\% 密度）时 \texttt{gp} 为 1.2 $\mu$s，相对稠密
815 $\mu$s 约 700$\times$；$k=512$ 时仍有 3.3$\times$。
$n\ge11$ 不构建符号表（n=14 的表会是 1 GiB），改为按需计算符号；
代价是每对约 15--50 ns，而不是查表的约 1 ns。
注意 sandwich 会先产生稠密中间结果，成本约为两次 \texttt{gp} 再加排序，
高维高密度下不是稀疏路径的强项。

\section{JMH 复核}
%%JMH%%

JMH 的平均值与既有 harness 一致（n=10 \texttt{gp} 约 0.89 ms）。
分配量在 n=3 时为 \texttt{gp} 80 B/op、\texttt{sandwich} 144 B/op，
即每次调用分配 1--2 个结果对象；维度升高时按 $2^n$ 增长。
批量与快速路径的单点成本低于逐元素调用，四线程下反而略慢，
说明该路径受内存带宽/分配限制，而不是 CPU 核数。

\section{稀疏鲁棒性与阈值}
%%ROBUST%%

均匀随机不是唯一负载。结构化输入（versor、PGA 点、CGA 点）在相同 $k$ 下
通常比均匀随机更便宜，但 sandwich 会先把中间结果稠密化：
n=10、k=32 时 versor 的 gp 为 4.3 $\mu$s，sandwich 为 27.0 $\mu$s；
n=12 同规模为 15.9 $\mu$s 与 519 $\mu$s。
混合密度下，1\% 稠密元素支配总时间：n=10 的 1000 次操作中
10 个稠密元素使均值从 2.0 $\mu$s 升到 49.7 $\mu$s。
动态相乘时 nnz 从 64 增长到约 500（n=10），时间从 0.7 到 11 $\mu$s 后趋于平台；
n=12 平台约 860 nnz、108 $\mu$s。n=14、k=512 的 gp 约 13--15 ms，
sandwich 约 388 ms；后者仍然只适合离线路径。

%%THRESHOLD%%

自动策略原先按“$4k^2<2^n$”选择哈希累加，在 n=14、k=32 时误判，
比稠密累加慢 2.6$\times$。加入符号表感知后（n$\le$10 用 4，n$>$10 用 16），
唯一的边缘误判是 n=12、k=16（约 13\%）。

\section{子掩码乘积（$4^n \to 3^n$）}
%%SUBMASK%%

外积、左缩并、右缩并的有效配对都只占全部配对的 $3^n/4^n$：
外积要求 $a\wedge b$ 的 blade 不重叠，左缩并要求 $a$ 的支撑是 $b$ 的子集，
右缩并反之。旧实现对每个 $a$ 扫描全部 $4^n$ 个 $b$ 再做位与判断；
现在按兼容性枚举子掩码，只访问有效配对，复杂度降到 $3^n$。
这与二叉树递归方法在外积上得到的 $O(3^d)$ 是同一个组合事实。

\begin{figure}[htbp]\centering
\includegraphics[width=0.74\textwidth]{figures/fig-submask.pdf}
\caption{子掩码枚举相对全扫描的加速比。}\label{fig:submask}
\end{figure}

n=10 时外积 633 $\mu$s $\to$ 77 $\mu$s（8.2$\times$），左/右缩并同量级；
n=8 为 5.6$\times$，n=3 为 1.6$\times$。几何积仍需访问全部配对，
保持不变；依赖外积的 \texttt{vee}、P3 平面/直线求交随之受益。

\section{多核扩展}
%%MULTICORE%%

测试机为 6P+8E、20 逻辑核。独立输入的 \texttt{gp}（n=10）在 8/14/20 线程
分别为 5.1$\times$/7.3$\times$/8.4$\times$，新 \texttt{op} 为 4.6$\times$/6.4$\times$/8.8$\times$；
两者每线程都分配结果对象，8 线程后受共享缓存、内存与 GC 限制。
批量 sandwich 在 4 线程即达到约 30 GB/s 的平台（2.3$\times$），更多线程无收益；
标量 sandwich 到 20 线程为 3.6$\times$（31.3→8.6 ns/点）。
因此批量路径应按 4--8 线程配置，通用 GA 计算可继续吃满剩余核心，但不要期待线性扩展。

\section{建议}
\begin{enumerate}
\item 几何积的 $4^n$ 稠密循环是唯一值得继续研究的算法瓶颈；单对成本已接近常数，
      进一步提升需要稀疏/分块表示，而不是微优化。
\item 符号表按需构建已消除 n$\ge$9 的 44$\times$ 悬崖；Cl(10) 首次乘法多一次建表开销。
\item 批量 API 用于 N$\ge$100 的批量变换；单元素保持使用不可变 API。
\item 渲染侧缓存 \texttt{Matrix4f}/\texttt{Quaternionf}，避免逐调用转换。
\item \texttt{inverse()} 仅用于 versor；一般元素和矩阵主元使用
      \texttt{inverseGeneral()}，并限制维度。
\item 本报告覆盖了 ga-benchmark 的大部分一元/二元运算，但该规范没有 Java 绑定，
      因此没有直接接入；横向比较对象为 JOML。
\end{enumerate}

\section{限制}
除第 16 节外为单线程；多核数据在 6P+8E、20 逻辑核上取得。非隔离环境，绝对纳秒
有 ±10\% 抖动；分配量来自 TLAB 计数，适合比较数量级；JOML 为 float，不是同精度
纯算术对比；未实现真实 SIMD（Java Vector API 仍为 incubator）。
